# Рішення, яких не було в брифі

Кожне — найпростіший варіант; змінюється одним правленням.

1. **`role`, `club`, `coach_full_name` у `shingi_profiles` допускають `NULL`.** Бриф вимагає `NOT NULL`, але також каже створювати профіль при першому вході «без ролі». Профіль вважається заповненим (`complete`), коли є всі три поля.
2. **Реєстрація бійців відкрита лише в статусі `registration`.** `announced` — лише показ лічильників. У `draft` заявки не приймаються.
3. **Місце в ліміті блоку займають заявки `submitted`, `paid`, `fought`.** `draft` і `withdrawn` місць не займають.
4. **Рік народження замість дати (`2012`)**: зберігається `age_years = рік події − рік народження`, `birth_date` порожня, у попередньому перегляді є попередження «вік приблизний».
5. **Повна дата народження**: зберігається `birth_date`, `age_years` порожнє; вік щоразу рахується на дату події.
6. **Парсер: колір пояса на початку рядка вважається прізвищем** («Білий Олег»), а не поясом. Колір береться лише точною формою слова (білий, синього…), тому «Білик» чи «Синюк» поясом не стають.
7. **Парсер: два числа без підписів — менше це вік, більше це вага** (за брифом «найбільше з двох = вага»).
8. **Сталі групування** (крок віку kids = 1, крок ваги kids = 5 кг, open = 10 кг) — значення за замовчуванням у `grouping.ts`; адмін може передати `kids_age_step`, `kids_weight_step`, `open_weight_step` у query.
9. **Групи формуються з заявок `submitted/paid/fought`.** Чернетки, зняті й неявки не групуються.
10. **Видалення бійця з оплаченою заявкою тренеру заборонене** (403, «напишіть організаторам»): інакше це обхід блокування `DELETE /entries/:id`. Без оплати — повне видалення разом із заявками. Бриф казав «лише `withdrawn`»; замість цього знімає оплачену заявку лише адмін через `PUT /admin/entries/:id`.
11. **Зняти бійця самому тренер може до оплати і до дедлайну внеску**, потім — лише адмін.
12. **Подія-заглушка при першій міграції:** `draft`, дата = сьогодні + 60 днів, дедлайни D−10 / D−7 / D−5. Адмін змінює дату.
13. **Вхід лише через `POST` (callback віджета `data-onauth`), без `data-auth-url`.** GET-редірект без перевірки Origin дозволяв залогінити жертву в чужий профіль. POST-входи (`auth/telegram`, `auth/webapp`) перевіряють Origin/Referer.
14. **Ручні дії адміна (`POST /admin/entries`, зміна статусу заявки) не беруть блокування події і не перевіряють ліміти** — це свідомий override організатора. Може випередити тренерську подачу при одночасних запитах.
15. **Масове додавання через `POST /entries` не міняє блок, вагу, пояс оплачених заявок**; зміна блоку в неоплачених враховується в лімітах.
16. **Тестовий запуск без фреймворку:** `npm run test:shingi` — вбудований `node --test` на нативному TypeScript Node 22.18+/24 (без `tsx`); невеликий хук `tests/shingi/ts-resolve.mjs` зіставляє імпорти `./x.js` з файлами `./x.ts`. Бо в репозиторії тестів не було.
